1. The big picture

The project has three layers. The story is data: JSON files in assets/data/. The library (include/hollow + src, the static library hollow::hollow) holds systems that know nothing about this particular story: a dialogue runner, a dialogue box, rooms, actors, effects. The game (apps/app) ties them together: the main loop, the rules for walking and using things, and small scripts for the rooms that need code.

Two rules keep this tidy:

  • Headers declare, src/ implements. Systems with a lot of state (StoryState, DialogueRunner, Audio) keep it behind a private Impl struct (d_ pointer); small value types have plain members.
  • The library never names a room, a character or a variable of this story. Anything story-specific lives in assets/data or apps/app.

2. Starting the program

  1. main() (apps/app/main.cpp) reads the command line: --check, --windowed, --room, --set, --screenshot, --walkthrough.
  2. It creates a Game with the path of assets/ next to the program and calls Game::load():
    • loadGameData() reads data/game.json and every file it lists into one GameData struct, collecting mistakes in a Diagnostics.
    • checkGameData() checks references across files (unknown conversation, variable, item, room, command verb).
    • The game also checks the conversations its room scripts start by name, and that each room's "script" exists.
    • Each declared variable goes into the StoryState; a DialogueRunner is created over all conversations, with Game::onCommand as its command handler.
  3. With --check it prints the problems and stops here (no window). This is the CTest test hollow.app.
  4. Otherwise it opens the window (borderless fullscreen unless --windowed), then Game::initGraphics() creates the 480×270 canvas, the 320×180 scene layer, the font, the audio device and the character sprite sheets.
  5. The loop: while (!WindowShouldClose() && !game.quitRequested()) game.frame(GetFrameTime()); In a walkthrough, Walkthrough::step() runs before each frame to press virtual keys.

3. One frame

Game::frame(dt) clamps dt to 0.1 s (so a stall never skips a timer), then calls update(dt) and draw(). Everything that moves happens in that order:

The three middle branches in detail

  • Inventory open: Tab/I opened InventoryPanel. It shows Game::inventory() (held items, plus items that follow a count variable such as cigarettes) and closes on Tab, I or Esc.
  • Conversation: the DialogueRunner decides what is on screen (a DialogueView); the DialogueBox decides how (typing, pages, options) and turns key presses into advance() or choose(i).
  • Exploring: A/D move the player, clamped by the room's walk range and by objects with an active block; pushing into a block plays its blocked conversation. E uses nearestTarget(); a click uses hoveredTarget() if it is in reach. Then updateTriggers() and, after 20–32 s of standing still, an idle bark.

4. Dialogue, conditions and effects

This is the heart of the game. Conversations are lists of entries (DialogueEntry). The runner walks them with a small stack (so then/else blocks can nest), and stops whenever something has to be shown.

How the runner moves

DialogueRunner::start(id) pushes the conversation and calls the private step(), which loops:

  • Take the next entry of the top list (pop finished lists). If its if is false, skip it (a block with else pushes the else list instead).
  • Line (speaker, thought, narration): fill the view, apply its do, stop until advance().
  • Choice: keep only options whose if is true and that have text; stop until choose(i), or until the timer runs out (update(dt) then takes the timeout option).
  • Pause: stop for N seconds (counted in update(dt)).
  • Block pushes then; Goto clears the stack and pushes the target; Action applies its effects and goes on; End clears everything.

Every new thing on screen increments DialogueView::serial. The DialogueBox watches that number: a new serial means “lay out the new text and ignore input this frame”, so one key press can never both open and skip a line.

If a command handler starts another conversation in the middle (for example a script reacting to an event), the runner notices through an internal generation counter and stops working on the old one.

Conditions and effects

Condition::parse() turns text like "x_condition <= 1 && item.bandages" into a small tree once, at load time; evaluate(state) walks the tree every time it is needed. Effect::parse() turns "cig_count += 1", "give key" or "sound crack" into a Set, Add, Give, Take or Command. StoryState::get() understands three kinds of name: declared variables, item.<id> and seen.<conversation>.

5. What the Game owns

Game (apps/app/game.hpp) is the one object that holds everything for the whole run. Room scripts get a Game& and use its public methods; nothing else is global.

6. Screen and coordinates

There are three sizes, and every drawing call uses one of them:

  • Scene pixels (0–320, 0–180, layout::SceneWidth, SceneHeight): rooms, objects, actors, apparitions, the foliage frame. The game draws them into the RenderLayer scene_, which Canvas::present() shows on the screen in the scene box (1.25 canvas pixels per scene pixel), shifted by the screen shake, under the canvas. Game::toCanvas() turns a scene point into canvas pixels; prompts and barks are drawn on the canvas with it, so all text has the same pixels.
  • Canvas pixels (0–480, 0–270): the HUD, dialogue box, inventory, menus, title and end card, prompts and barks. Constants are in hollow::layout (ui/theme.hpp). In a room the canvas is cleared see-through and drawn with colours multiplied by alpha, so a fade or a dimmed scene covers the scene under it as it should.
  • Screen pixels: only Canvas::present() and Canvas::toCanvas() know them. Input converts the mouse to canvas pixels at once; the game subtracts the scene box origin to test clicks on objects.

9. Walk-throughs of real moments

9.1 The player presses E next to the medical kit

  1. Input::update sees E down this frame: pressed(Action::Interact) is true.
  2. No conversation and no inventory, so updatePlaying calls updateExploring. nearestTarget() checks every usable() object (present by its if, interactive, not used up) whose x-range ±6 px contains the player, and picks the closest centre: the kit.
  3. interact(kit): turns the player towards it, counts the use (useCount_); the first use plays dialogue (campsite.kit), later ones again. startDialogue() stops barks, consumes the key press and calls DialogueRunner::start.
  4. The runner shows the first line. Next frame the DialogueBox sees a new serial, wraps “Y: One bandage…” and starts typing at 45 letters a second.
  5. At the line “Got: Last Bandage.” the entry's do runs: give last_bandage and kit_taken = true change the StoryState directly.
  6. After the last line the view becomes None; the game is exploring again. Talking to X now offers “Apply the Last Bandage.” because that option's if is item.last_bandage.

9.2 A room change

  1. Using an exit object: if its exit_if is true, goTo(room, spawn_x); otherwise its locked conversation plays. A dialogue can also do goto <room>.
  2. goTo stores the room and starts fade_ towards black (0.45 s). While it is pending, busy() is true and nothing reacts to input.
  3. When the fade is fully black, enterRoom: creates the room's script, places the player and X (by the room's companion mode), sets tint and ambient sounds, lights burning fires at full strength, calls script->enter, then runEnterRules (all matching rules apply their effects; the first with a conversation starts it). The fade goes back to clear.

9.3 A timed choice (the factory creature)

  1. The trigger object encounter (an invisible zone, if: !factory_cleared) fires when the player walks into it: updateTriggers starts floor.encounter.
  2. A then/else block picks the 4-second or the 7-second choice by noisy_entry. Options with an if appear only with the bolt, the bat, or the pistol and rounds.
  3. DialogueRunner::update counts the time down; the box draws a shrinking line. If time runs out, the hidden timeout option (no text) is taken: floor.seen.
  4. The chosen branch runs commands: event creature_leave 360 (to CreatureRoomScript) or event creature_guard 262 and step y -70; variables record what happened for later rooms.

9.4 Stealth at the checkpoint

  1. The arrival conversation ends with event stealth_start; CheckpointScript becomes active.
  2. Each frame (while not busy) PhaseLoop advances through the room's phases. The creature's look follows the phase; a phase with to walks it there.
  3. Game::coverAt(player.x) tells whether the player stands inside a cover object. Hidden players kneel; covers are drawn front, so they hide the player.
  4. Danger: phase watch and not in cover, or phase listen and the player moved this frame. Danger fills suspicion_; at 0.4 s the player is spotted (a short grace window). A dim “!” blinks 0.9 s before each dangerous phase.
  5. Spotted: spotted_count += 1, shake, and checkpoint.spotted (whose lines cost x_condition the second time). It ends with event stealth_reset: both back at the last hiding spot, the loop restarts. The third time it is checkpoint.chase, which always ends in the next room.

9.5 Dragging X

  1. companion drag (a dialogue command) calls setCompanionMode(Drag): the player's pose becomes drag and speed 45%, X lies down, and the variable dragging becomes 1.
  2. updateCompanion keeps X on the side the player walks away from.
  3. Because dragging is a normal variable, data can react to it: the narrow gap is "block": "dragging && !turned_x", rest spots are "if": "dragging", exits are "exit_if": "dragging". No code knows about these places.

9.6 Drawing a frame

  1. drawScene renders into the 320×180 layer: background (or the room's colour and a darker ground band), the script's back layer (the creature), objects behind, X, the player, objects in front, lights, particles, the script's front layer (apparitions), then the room's foliage frame ("frame": true).
  2. The canvas, cleared see-through, gets the bark and the “[E] Name” prompt, the bars, then the dialogue box, inventory, or the room name and keys; the fade covers everything; pause draws over it.
  3. Canvas::present picks the scale: the biggest whole number if that leaves 10 % of the screen black or less, otherwise the canvas fills the screen as far as its shape allows. It draws the scene in the scene box, then the canvas over it. A fractional scale is drawn by the next whole number first and then smoothly down (Enlarger), so every art pixel stays the same size.
One idea runs through all of this: the code provides mechanisms (conditions, effects, blocks, triggers, exits, companion modes, timed choices) and the JSON decides where they happen. Only things that need a clock or a shape on screen (a timer, a patrol, an apparition) live in a room script.

10. Changing and extending

To…Change
add or change lines, choices, objects, roomsdata only: assets/data/, then game --check. Format: docs/DATA-FORMAT.md.
add a story variabledata declare it in game.json → variables; use it in any if / do.
add a dialogue commandapp add the verb to Game::commands() and handle it in Game::onCommand().
add a room scriptapp a class derived from RoomScript in scripts/, a line in makeRoomScript() and roomScriptNames(), the file in apps/app/CMakeLists.txt; conversations it starts by name go in Game::scriptConversations() so --check verifies them.
add a new kind of entry or object fieldlibrary the struct (dialogue.hpp / room.hpp), its parsing and checking in src/data/game_data.cpp, the behaviour in the runner or the game.
verify the game still finishesctest runs the unit tests, the data check and both walkthroughs (tests/walkthrough/full.txt, careless.txt).
